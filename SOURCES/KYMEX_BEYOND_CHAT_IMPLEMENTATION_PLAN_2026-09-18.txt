KYMEX AI — BEYOND CHAT NEW MODIFICATION & IMPLEMENTATION MASTER PLAN
Developer Implementation Specification — Multidomain AI Workspace,
Research Engine, Visual Intelligence, Reference Intelligence, and
Productivity Platform

DOCUMENT STATUS This is a NEW, SEPARATE implementation and modification
plan. It is intentionally different from the existing KYMEX AI master
prompt/documentation. It should be treated as an implementation
roadmap/specification that can be applied to KYMEX AI without replacing
the existing KYMEX AI product definition.

CORE VISION

KYMEX AI should not be designed as merely a chatbot with a message box.
It should operate as a multimodal AI work platform that can understand
text, documents, books, images, barcodes, QR codes, visual references,
structured identifiers, websites, products, organizations, tools,
equipment, brands, companies, and other real-world references.

The product should let a user move naturally from: QUESTION →
IDENTIFICATION → RESEARCH → VERIFICATION → ANALYSIS → EDITING → ACTION →
SAVED RESULT.

The interface may still contain a chat, but chat is only one entry point
into a much larger system.

The system must distinguish: 1. Information it directly extracted. 2.
Information retrieved from connected or approved sources. 3. Information
inferred by the AI. 4. Information supplied by the user. 5. Information
that could not be verified.

Never fabricate a book, ISBN record, barcode meaning, QR payment
destination, company identity, tool specification, or other reference.

============================================================ 1.
MULTIMODAL INPUT & UNDERSTANDING
============================================================

1.1 Text - Natural-language questions. - Long-form prompts. - Structured
commands. - Code and technical notation. - Tables pasted into chat. -
Mixed-language prompts where supported.

1.2 Images - Upload photographs, screenshots, scans, diagrams, receipts,
labels, products, pages, forms, whiteboards, charts, maps, and
handwritten material. - Understand visible text using OCR. - Detect
objects and relevant regions. - Allow the user to select/crop a region
before analysis. - Preserve the original upload and create derived
working copies.

1.3 Documents - PDF, DOCX, PPTX, XLSX, CSV, TXT, Markdown and supported
image-based documents. - Extract text, tables, headings, metadata, page
references, figures and relevant structural information. - Maintain
page/section provenance so answers can point back to source material.

1.4 Camera-first workflow Provide an optional Scan action: Scan → Detect
→ Identify → Verify → Explain → Save/Act.

============================================================ 2. BOOK
INTELLIGENCE
============================================================

2.1 Book preview KYMEX AI should be able to generate a useful book
preview when enough information is available: - Title. - Author(s). -
Edition. - Publisher. - Publication date. - ISBN-10 / ISBN-13 where
applicable. - Language. - Page count when verified. -
Subjects/categories. - Description. - Table of contents when
available. - Cover image where legally available. - Edition
differences. - Available formats when sourced. - User-uploaded pages or
excerpts. - Reading-level or study-oriented metadata when available.

The preview must clearly distinguish bibliographic facts from
AI-generated commentary.

2.2 Author + ISBN lookup The user should be able to enter: “[Author]
[ISBN]” and have KYMEX AI resolve the identifier against configured
bibliographic/reference sources.

Resolution pipeline: Normalize ISBN → validate checksum → search sources
→ reconcile records → detect edition → return confidence/provenance →
present result.

2.3 ISBN behavior Support: - ISBN-10. - ISBN-13. - Hyphenated ISBNs. -
ISBN entered from OCR. - ISBN copied from a webpage. - Invalid or
incomplete ISBN handling. - Multiple editions with clear
differentiation.

Do not assume two ISBNs represent the same edition.

2.4 Book page analysis When a user uploads book pages, KYMEX AI should
support: - Page transcription. - Chapter identification. - Summary. -
Concept extraction. - Definitions. - Study questions. - Flashcards. -
Citation/page references. - Compare pages or editions. - Explain
difficult passages. - Extract tables and diagrams. - Search within
uploaded book material.

2.5 Copyright-aware book handling The system should support metadata,
previews, user-provided material, summaries, analysis and
transformations within applicable rights and platform rules. It must not
falsely claim access to a full copyrighted book merely because metadata
exists.

============================================================ 3. BARCODE
INTELLIGENCE
============================================================

Implement barcode scanning through camera and uploaded images.

Support a provider abstraction for common barcode families where
technically appropriate, including: - UPC-A / UPC-E. - EAN-8 / EAN-13. -
Code 39 / Code 128. - ITF. - ISBN represented by EAN. - Other formats
supported by the selected scanning SDK.

Pipeline: Capture image → locate barcode → decode → normalize → identify
type → query appropriate reference source → reconcile results → display
details.

For retail products, results can include: - Product name. - Brand. -
Manufacturer. - Product identifier. - Category. - Variant/size when
available. - Country/market information when verified. - Packaging
information. - Product images from permitted sources. - User notes.

A barcode value is an identifier, not proof of every product attribute.
Source provenance must remain visible.

============================================================ 4. QR CODE
INTELLIGENCE
============================================================

Implement QR detection and decoding for: - URLs. - Text. - Contact
information. - Wi-Fi configuration. - Email/SMS payloads. - App/deep
links. - Payment-related QR payloads where supported. - Other standards
supported by the decoder.

4.1 Payment QR workflow When a QR appears to encode payment
information: - Decode the payload. - Identify the apparent payment
standard/network where possible. - Extract merchant/payee information
present in the payload. - Extract amount/currency/reference information
when encoded. - Display the raw decoded payload in an inspectable
technical view. - Explain what each field means. - Show warnings when
fields are missing, unusual, malformed, or inconsistent.

Never state that a QR payment destination is safe merely because the
code decoded successfully.

Before any financial action: - Require explicit user confirmation. -
Show destination details. - Do not silently initiate a payment. - Keep
payment execution separate from QR analysis. - Apply authentication,
fraud checks, transaction limits and provider controls.

4.2 QR security Detect suspicious URL patterns, mismatched domains,
encoded redirects and other observable warning signs where possible.
Clearly label heuristic warnings as heuristics rather than proof of
fraud.

============================================================ 5. IMAGE
EDITING & VISUAL MODIFICATION
============================================================

KYMEX AI should provide an image workspace, not only image description.

Capabilities: - Crop. - Resize. - Rotate. - Straighten. - Remove or
replace background. - Remove selected objects where supported. - Restore
damaged areas. - Clean scans. - Enhance legibility. - Upscale where
supported. - Adjust brightness, contrast, exposure and sharpness. -
Convert formats. - Redact selected sensitive information. - Remove glare
where technically feasible. - Perspective correction for photographed
documents. - Color correction. - Selective editing through
natural-language instructions. - Generate modified variants while
preserving the original.

Example: “Remove the background, keep the product unchanged, make the
label clearer and export a square version.”

The system should show: Original → Working version → Generated/edited
version → Export.

For edits affecting identity, documents, evidence, financial records or
other high-stakes material, preserve the original and make modifications
clearly distinguishable.

============================================================ 34. EXAMPLE
USER JOURNEYS
============================================================

Journey A — Student + Book User scans a book barcode. KYMEX identifies
the ISBN. KYMEX resolves the edition. User opens Book Preview. User
uploads two pages. KYMEX explains them and creates flashcards. User
exports a study sheet.

Journey B — Retailer User scans a product barcode. KYMEX resolves
product identity. User confirms the product. KYMEX creates a catalog
record using the retailer’s internal SKU. User generates a product
description and label.

Journey C — Engineer User photographs equipment. KYMEX extracts
model/reference information. It presents candidate matches and source
evidence. User selects the verified model. KYMEX retrieves the available
public specifications/manual references. User asks for a maintenance
checklist.

Journey D — Office Worker User uploads a meeting transcript. KYMEX
extracts decisions, tasks, owners and deadlines. User reviews them.
KYMEX creates a structured action list.

Journey E — QR Analysis User scans a QR. KYMEX identifies it as a
payment-related payload. It displays the decoded fields and warnings. No
payment is initiated automatically. The user may explicitly proceed
through the connected payment workflow if one is available and
authorized.

Journey F — Developer User uploads an error log and relevant source
files. KYMEX identifies likely failure points, cites relevant
files/lines, proposes a patch and generates tests. The user reviews
before applying changes.

============================================================ 35. FINAL
PRODUCT PRINCIPLE
============================================================

KYMEX AI should feel like a universal AI workbench rather than a
conventional chatbot.

The design goal is not: “Ask KYMEX a question.”

The design goal is: “Bring KYMEX whatever I am working with — a
question, book, barcode, QR code, image, document, product, tool,
company, reference number, spreadsheet, codebase or business task — and
let it help me understand it, verify it, transform it, organize it and,
when authorized, act on it.”

The implementation should therefore optimize for: UNDERSTANDING +
IDENTIFICATION + VERIFIED KNOWLEDGE + CREATION + TRANSFORMATION +
PRODUCTIVITY + AUTHORIZED ACTION.

This document is a separate modification/implementation plan. It should
complement the existing KYMEX AI documentation rather than overwrite it.

============================================================ 50. GOOGLE
AI STUDIO IMPLEMENTATION TARGET
============================================================
The implementation should be designed with Google AI Studio as the
primary development environment.

The architecture should remain modular rather than hard-coding the
entire product around a single model.

Implementation guidance: - Use Gemini capabilities available through the
chosen Google AI development stack for multimodal understanding,
reasoning, document/image analysis and generation where appropriate. -
Use structured outputs for extraction tasks. - Define explicit schemas
for ISBN, barcode, QR, invoice, receipt, product, book, company and
entity results. - Use function/tool calling for external actions. - Keep
secrets and server credentials out of client-side code. - Place
privileged operations behind a backend. - Use environment configuration
for API keys. - Implement provider interfaces so additional AI or data
providers can be introduced later. - Use streaming responses for
interactive experiences where useful. - Use asynchronous jobs for long
image/document/research tasks. - Validate model-generated structured
data before writing it to the database. - Log tool calls and high-impact
actions according to the security model.

Google AI Studio should be treated as the development
environment/orchestration starting point, while the production
architecture should remain portable enough to evolve.

============================================================ 58. FEATURE
DISCOVERY PRINCIPLE
============================================================

The implementation team must not interpret this document as a closed
list.

When implementing each workspace, developers should identify additional
high-value workflows that naturally follow from the role, the connected
tools, and the platform’s capabilities.

The governing question is:

“What repetitive, information-heavy, document-heavy,
communication-heavy, research-heavy, scheduling-heavy, or
decision-support task does this user perform that KYMEX can safely
reduce to a simple workflow?”

Add those capabilities through modular tools, templates and workflows
without breaking permission boundaries.

The goal is to make the workspaces genuinely useful professional
environments, not themed versions of the same chat screen.
